# Key sources
{: .no_toc }

Everything is encrypted with keys derived from a single **root key**. Where that root key comes from is the main decision you make when setting up the library. You configure it in `AddEncryption`, and you can only use one source per application.

Here's how the three options compare:

| | Static key | AWS KMS | Your own key management |
|---|---|---|---|
| Configure with | `UseKey(key)` | `UseAwsKms(keyId)` | `UseKeyWrapper<T>()` |
| Package | core | `EntityFrameworkCore.Encrypted.AwsKms` | core |
| Root key | the key you configure, shared by all contexts | generated by KMS, one per context | generated by your service, one per context |
| Who can see the plaintext key | whoever can read your configuration | only KMS and your app's memory | only your service and your app's memory |
| External calls | none | one `kms:Decrypt` per context at startup | one unwrap per context at startup |
| Rotation | add a key with a higher id | `RotateRootKeyAsync` | `RotateRootKeyAsync` |

If you're not sure which to pick: a static key is perfectly fine for getting started and for smaller apps. Move to a key management service once you want the key out of your configuration, or need access control and auditing.

## Static key

A static key is a 32-byte AES-256 key that you keep in your configuration or secret store. It's simple and doesn't depend on any external service. The trade-off is that your app holds the key itself, so anyone who can read your configuration can read your data.

```csharp
builder.Services.AddEncryption(x => x.UseKey(builder.Configuration["Encryption:Key"]!));
```

`UseKey` accepts a Base64 string or a `byte[]`. To generate a key:

```csharp
Convert.ToBase64String(RandomNumberGenerator.GetBytes(32));
```

### Rotating a static key

Each key has an id, which defaults to 1. To rotate, add the new key with a higher id and keep the old one around. The key with the highest id encrypts new values, and the others are only used to read older values.

```csharp
builder.Services.AddEncryption(x => x
    .UseKey(builder.Configuration["Encryption:Keys:1"]!, id: 1)
    .UseKey(builder.Configuration["Encryption:Keys:2"]!, id: 2));
```

Once you've [re-encrypted](key-management#re-encrypting-existing-values) the existing data and [checked](key-management#key-usage) that nothing uses the old key anymore, you can remove it.

## AWS KMS

With AWS KMS, your app never sees the master key. KMS generates a root key for each context the first time it starts. The library stores that root key in the context's own `__EncryptionKeys` table, wrapped (encrypted) by your KMS key. Only KMS can unwrap it, and your database backups automatically contain the keys they need.

```bash
dotnet add package EntityFrameworkCore.Encrypted.AwsKms
```

```csharp
builder.Services
    .AddEncryption(x => x.UseAwsKms("arn:aws:kms:eu-west-1:123456789012:key/1234abcd-..."))
    .AddDbContext<AppDbContext>(x => x.UseNpgsql(connectionString).UseEncryption());
```

You can pass a key ARN, a key id or an alias like `alias/orders`. At startup each context's root key is unwrapped with one call to `kms:Decrypt` and then kept in memory, so KMS isn't involved when you read or write values.

### The AWS client

If you've registered an `IAmazonKeyManagementService` yourself, the library uses it. Otherwise it creates one from your normal AWS configuration (the `AWS` section in `appsettings.json`, environment variables, or the instance role).

Registering it yourself is handy for LocalStack in development:

```csharp
builder.Services.AddSingleton<IAmazonKeyManagementService>(new AmazonKeyManagementServiceClient(
    new BasicAWSCredentials("test", "test"),
    new AmazonKeyManagementServiceConfig { ServiceURL = "http://localhost:4566", AuthenticationRegion = "us-east-1" }));
```

### Encryption context

Every call to KMS includes an encryption context with the root key id, so one wrapped key can't be swapped for another. You can add your own entries too. They show up in CloudTrail, and you can use them in IAM conditions to limit which app can unwrap which keys:

```csharp
x.UseAwsKms(kms => kms
    .WithKeyId("alias/orders")
    .WithEncryptionContext("service", "orders"));
```

{: .warning }
The encryption context becomes part of every wrapped root key. If you change it later, the existing root keys can't be unwrapped anymore. Keys that start with `efenc:` are reserved for the library.

### IAM permissions

| Permission | Needed for |
|------------|------------|
| `kms:Decrypt` | startup, and reading values encrypted with an older root key |
| `kms:GenerateDataKey` | the very first start, and `RotateRootKeyAsync` |
| `kms:ReEncryptFrom` on the old key, `kms:ReEncryptTo` on the new one | `RewrapRootKeysAsync` |

A typical policy for the app looks like this:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
      "Resource": "arn:aws:kms:eu-west-1:123456789012:key/1234abcd-...",
      "Condition": { "StringEquals": { "kms:EncryptionContext:service": "orders" } }
    }
  ]
}
```

If an app should only ever read existing keys, give it just `kms:Decrypt` and turn off key creation. A missing key then shows up as an error instead of a new key being created by accident:

```csharp
x.UseAwsKms(keyId).CreateRootKeyIfMissing(false);
```

### Rotating the KMS key

Turn on [automatic key rotation](https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html) in KMS. KMS keeps the previous key material around, so there's nothing to do in your app. If you need to move to a completely different KMS key, see [Moving to another KMS key](key-management#moving-to-another-kms-key).

## Custom key management

You can plug in any key management service, such as Azure Key Vault, Google Cloud KMS, HashiCorp Vault or an HSM, by implementing `IKeyWrapper`. Everything else works the same way it does with AWS KMS: the `__EncryptionKeys` table, caching, rotation, refresh, re-encryption and rewrapping.

The interface has three methods:

```csharp
public interface IKeyWrapper
{
    // create a new AES-256 root key and return it both as plaintext and wrapped
    Task<GeneratedRootKey> GenerateAsync(int rootKeyId, CancellationToken cancellationToken);

    // unwrap a stored root key
    Task<byte[]> UnwrapAsync(WrappedRootKey rootKey, CancellationToken cancellationToken);

    // wrap an existing root key with the key you currently have configured
    Task<WrappedRootKey> RewrapAsync(WrappedRootKey rootKey, CancellationToken cancellationToken);
}
```

Register your implementation:

```csharp
builder.Services.AddEncryption(x => x.UseKeyWrapper<KeyVaultKeyWrapper>());

// or, if you want to build it yourself
builder.Services.AddEncryption(x => x.UseKeyWrapper(sp => new KeyVaultKeyWrapper(...)));
```

It's registered as a singleton and can take dependencies from the container.

`WrappingKeyId` tells you which key wrapped a root key, for example a key URL. It's stored next to the wrapped key and handed back to you when unwrapping, so root keys wrapped by an older key keep working after you switch to a new one.

### Example: Azure Key Vault

Here's a sketch of a wrapper for Azure Key Vault using `Azure.Security.KeyVault.Keys` and an RSA key. Adapt it to your setup:

```csharp
public sealed class KeyVaultKeyWrapper(KeyClient keys, IConfiguration configuration) : IKeyWrapper
{
    private string KeyName => configuration["Encryption:KeyVaultKey"]!;

    public async Task<GeneratedRootKey> GenerateAsync(int rootKeyId, CancellationToken ct)
    {
        var rootKey = RandomNumberGenerator.GetBytes(32);
        var wrapped = await Client(await GetKeyIdAsync(ct)).WrapKeyAsync(KeyWrapAlgorithm.RsaOaep256, rootKey, ct);
        return new GeneratedRootKey(rootKey, wrapped.KeyId, wrapped.EncryptedKey);
    }

    public async Task<byte[]> UnwrapAsync(WrappedRootKey rootKey, CancellationToken ct)
        => (await Client(rootKey.WrappingKeyId).UnwrapKeyAsync(KeyWrapAlgorithm.RsaOaep256, rootKey.WrappedKey, ct)).Key;

    public async Task<WrappedRootKey> RewrapAsync(WrappedRootKey rootKey, CancellationToken ct)
    {
        var plaintext = await UnwrapAsync(rootKey, ct);
        try
        {
            var wrapped = await Client(await GetKeyIdAsync(ct)).WrapKeyAsync(KeyWrapAlgorithm.RsaOaep256, plaintext, ct);
            return rootKey with { WrappingKeyId = wrapped.KeyId, WrappedKey = wrapped.EncryptedKey };
        }
        finally
        {
            CryptographicOperations.ZeroMemory(plaintext);
        }
    }

    // the versioned key id, so root keys wrapped by older key versions stay readable
    private async Task<string> GetKeyIdAsync(CancellationToken ct)
        => (await keys.GetKeyAsync(KeyName, cancellationToken: ct)).Value.Id.ToString();

    private CryptographyClient Client(string keyId)
        => keys.GetCryptographyClient(KeyName, new KeyVaultKeyIdentifier(new Uri(keyId)).Version);
}
```

### Storing keys somewhere else

By default, wrapped root keys live in the `__EncryptionKeys` table of each context. If you'd rather keep them somewhere central, implement `IRootKeyStore`:

```csharp
builder.Services.AddEncryption(x => x
    .UseKeyWrapper<KeyVaultKeyWrapper>()
    .UseRootKeyStore(sp => new MyRootKeyStore(...)));
```

```csharp
public interface IRootKeyStore
{
    // throw EncryptionKeyStoreUnavailableException if the store isn't ready yet (e.g. not migrated)
    Task<IReadOnlyList<WrappedRootKey>> GetAllAsync(Type dbContextType, CancellationToken cancellationToken);

    // return false if a key with this id already exists, because another instance just created it
    Task<bool> TryAddAsync(Type dbContextType, WrappedRootKey rootKey, CancellationToken cancellationToken);

    Task UpdateAsync(Type dbContextType, WrappedRootKey rootKey, CancellationToken cancellationToken);
}
```

Make sure `TryAddAsync` is atomic, for example with a unique key on the context and the root key id. When several instances start at the same moment, exactly one of them should win.

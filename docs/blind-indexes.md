# Blind indexes
{: .no_toc }

Encrypted columns can't be compared in the database, so a plain `Where(x => x.Email == email)` doesn't work on them. A blind index fixes that for equality. It lets you look up rows by an encrypted value with a normal LINQ query, and the lookup uses a database index.

{:toc}

## Turning it on

Add `[BlindIndex]` next to `[Encrypted]`:

```csharp
public class Customer
{
    [Encrypted, BlindIndex]
    public string Ssn { get; set; } = null!;
}
```

Or configure it fluently. That's also where you can normalize values, for example to match emails regardless of case and surrounding spaces:

```csharp
modelBuilder.Entity<Customer>()
    .Property(x => x.Email)
    .IsEncrypted()
    .HasBlindIndex(v => v.Trim().ToLowerInvariant());
```

Then add a migration. It adds an indexed `Email_Index` column next to `Email`:

```bash
dotnet ef migrations add AddEmailBlindIndex
```

There's nothing else to configure. The key for the index is created and stored automatically, whichever [key source](key-sources) you use.

## Querying

Write the query you'd write for a normal column:

```csharp
var customer = await db.Customers.SingleOrDefaultAsync(x => x.Email == email);

var customers = await db.Customers.Where(x => emails.Contains(x.Email)).ToListAsync();

await db.Customers.Where(x => x.Email != email).CountAsync();

await db.Customers.Where(x => x.Email == email).ExecuteDeleteAsync();
```

The library rewrites these to compare the index column, and EF hashes your parameter the same way:

```sql
SELECT ... FROM "Customers" WHERE "Email_Index" = @email
```

With the normalization above, `" JANE@Example.com"` finds `jane@example.com`.

It only supports equality: `==`, `!=`, `Equals` (`x.Email.Equals(email)`, `string.Equals(x.Email, email)`) and `Contains` with a value or a list of values. `Equals` with a `StringComparison` throws, since the index is compared byte by byte; use the normalization for case-insensitive lookups. `StartsWith`, `LIKE`, sorting, ranges and comparisons with other columns still throw, because a hash can't answer those questions.

Enums and other converted types work too. The value is converted first, then normalized and hashed:

```csharp
e.Property(x => x.Status).HasConversion<string>().IsEncrypted().HasBlindIndex();

db.Customers.Where(x => x.Status == CustomerStatus.Blocked);
```

## Keeping the index up to date

You never set the index column yourself:

| You do | The index |
|--------|-----------|
| add an entity | is computed from the value |
| change the value and call `SaveChanges` | is recomputed |
| set the value to `null` | becomes `NULL` too |
| attach a detached entity with `Update` | is recomputed |
| change the value in your own `SaveChanges` interceptor | is computed from the value that's saved |
| `ExecuteUpdate(s => s.SetProperty(x => x.Email, value))` | is updated in the same statement |
| rotate keys, re-encrypt or rewrap | stays as it is, and lookups keep working |

`ExecuteUpdate` has one limit: it can set the value to a constant or a parameter, but not to an expression over other columns (`s.SetProperty(x => x.Email, x => x.Login)`). The database can't compute the hash, so that throws instead of leaving a stale index.

## Adding an index to existing data

When you add a blind index to a column that already has values, existing rows get an empty index column, and lookups won't find them yet. Fill it with:

```csharp
long updated = await app.Services.RebuildBlindIndexesAsync<AppDbContext>();
```

It works like [re-encryption](key-management#re-encrypting-existing-values), with the same [options to control the load](key-management#controlling-the-load) and progress logs. It runs in batches, it's safe while the app is running, and it can be stopped and restarted. It only writes rows whose index is missing or out of date, and clears indexes left behind on rows whose value is now `NULL` (for example, set with SQL).

Run it again whenever you change the normalization function, since existing rows were hashed with the old one.

## Keys and rotation

Every context gets its own blind index key, separate from the keys that encrypt values. That's what keeps lookups working when you rotate:

- **Root key and data key rotation** don't affect it, so nothing needs to be recomputed.
- **AWS KMS or a custom key wrapper:** the index key is generated by your key management service the first time it's needed, and stored wrapped in `__EncryptionKeys` next to the root keys. `RewrapRootKeysAsync` moves it to a new KMS key along with them.
- **Static keys:** the index key is generated randomly and stored in `__EncryptionKeys`, encrypted with a key derived from the active static key. When a new static key becomes active, the index key is rewrapped with it automatically on the next start. Once that start has happened, you can remove the old key as usual.

Each column also uses its own key derived from the index key, so the same value in two different columns gets two different hashes.

## What it reveals

A blind index is an HMAC-SHA256 of the value. Without the key, nobody can reverse it or test guesses against it, even for short values like phone numbers. It's still deterministic, though: equal values have equal hashes. Someone with database access can see which rows share a value and how often each value occurs, without knowing what the value is.

So use it for columns with many distinct values that you need to look up: emails, phone numbers, tax ids, document numbers. Don't use it for columns with only a few possible values, like a status, a country or a yes/no flag. With a database dump, counting is enough to guess those.

## Limitations

- Equality only: no prefix search, ranges or sorting.
- Properties of entity types, including owned types, but not of complex types or types mapped to JSON yet.
- Normalization works on values stored as strings, not on binary values.
- Raw SQL that writes encrypted columns doesn't update the index (it can't write valid encrypted values either).
